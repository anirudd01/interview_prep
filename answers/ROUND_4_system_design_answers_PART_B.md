## PART 1 — CLASSIC / BLANKET DESIGNS

### 1. Design a URL shortener. Then: 100k writes/sec, custom aliases, analytics, and link expiry. Where does it stop being trivial?
**Clarify**: read/write ratio (typically 100:1), short code length, custom aliases allowed, expiry, analytics depth (clicks only or geo/device/referrer, real-time?), redirect type (301 is cacheable by browsers so you lose analytics; **302** keeps you in the loop), abuse/malware filtering.
**Numbers**: 100k writes/s ≈ 8.6B links/day (huge; typical real systems are far smaller, so say so). Reads at 100:1 = 10M redirects/s, which must be served from cache/edge. Storage: ~500 bytes/link → 8.6B × 500B ≈ 4.3 TB/day. Code space: base62 with 7 chars = 62^7 ≈ 3.5 trillion, enough for ~1 year at this rate; use 8 chars for headroom.
**API**: `POST /links {long_url, custom_alias?, expires_at?}` → `{code}`; `GET /{code}` → 302; `GET /links/{code}/stats`.
**Data**: `links(code PK, long_url, owner_id, created_at, expires_at)` in a **key-value store partitioned by code** (DynamoDB/Cassandra/Cosmos), since access is always by key and the volume exceeds one Postgres. Clicks go to an analytics pipeline, not this table.
**Architecture**: client → CDN/edge → stateless API → cache (Redis, plus edge caching of hot redirects) → KV store. Click events → Kafka → stream aggregation (Flink/ClickHouse) → analytics store.
**Deep dives**:
- **ID generation at 100k/s, no collisions**: (a) a counter range allocator: each app instance leases a block of 1M IDs from a coordinator (a DB row / ZooKeeper / Redis `INCRBY`), then base62-encodes locally (no per-write coordination, and the codes are unique); obfuscate with a bijective shuffle so codes aren't guessable/sequential; or (b) random 8-char codes with conditional insert (`put-if-absent`) and retry on the rare collision. Hashing the URL (MD5 → take 7 chars) needs collision handling too and makes the same URL always get the same code, which may not be desired per user.
- **Custom aliases**: same table, conditional write `IF NOT EXISTS`; reserved words blocklist; aliases in the same namespace as generated codes, so the generator must avoid them (e.g. generated codes have a fixed length/prefix that custom ones can't use).
- **Analytics**: never write on the redirect path synchronously. Emit an event (async, buffered) to Kafka; aggregate per code/minute in a stream processor; store in an OLAP store (ClickHouse/Druid). Accept slight loss of click events if the producer buffer is lost (or make it durable if analytics are billable).
- **Expiry**: store `expires_at`; check at read time (return 404/410) so expiry is exact; delete lazily with the KV store's **TTL** feature; cache TTL ≤ time to expiry.
**Failure modes**: cache stampede on a viral link (request coalescing, edge caching), hot partitions (a viral code: replicate in cache, read from edge), ID allocator unavailable (instances hold pre-leased blocks), abuse (rate limit creation, scan URLs against Safe Browsing).
**Where it stops being trivial**: not at the basic design. It stops being trivial at **(1) unique ID generation at 100k writes/s across many nodes**, **(2) analytics at 10M events/s without slowing redirects**, **(3) hot-key caching for viral links**, and **(4) abuse/spam** (the real operational problem for public shorteners).

### 2. Design a parking lot system. (Start OO/API design, then push to distributed: 500 lots, real-time availability, reservations, and payments.)
**OO design (single lot)**: `ParkingLot` has `Levels`, each with `Spots` (type: compact/regular/large/EV/disabled). `Vehicle` (type) → a spot-assignment strategy (nearest free spot of compatible size). `Ticket` (entry time, spot, vehicle) → `Payment` (pricing strategy: hourly, flat, dynamic). Entry/exit `Gates`. Patterns: Strategy (pricing, spot allocation), State (spot: free/reserved/occupied/out-of-service), Observer (display boards update on spot change). Key invariant: **one vehicle per spot**, assignment must be atomic.
**Distributed version: clarify**: are spots individually tracked (sensors/cameras) or just counts per lot? Reservation for a time window, or "hold a spot now"? Payment at exit, prepay, or both? Do lots need to work offline if the network to the cloud drops? (Yes: a gate can't stop working.)
**Numbers**: 500 lots × ~500 spots = 250k spots. Events: entries/exits maybe 1–5M/day ≈ ~50/s peak. Availability reads from apps: maybe 1–2k/s peak. Small scale: a single Postgres handles it; the hard parts are **correctness and offline**, not throughput.
**API**: `GET /lots?near=lat,lon` (availability), `POST /reservations {lot_id, spot_type, start, end}`, `POST /entries {lot_id, plate|ticket}`, `POST /exits`, `POST /payments`.
**Data**: `lots`, `spots(lot_id, spot_id, type, state)`, `reservations(id, lot_id, spot_type, start, end, status)`, `sessions(id, lot_id, plate, entry_at, exit_at, spot_id)`, `payments(id, session_id|reservation_id, amount, status, idempotency_key)`.
**Architecture**: an **edge controller per lot** (gates, sensors, ANPR cameras, local DB) that works autonomously and syncs events to the cloud (an outbox → queue). Cloud: reservation service + availability service + payment service + Postgres; availability cached in Redis per lot/spot type, pushed to apps via websockets/polling.
**Deep dives**:
- **Reservations without overbooking**: count-based inventory per (lot, spot type, time slot): `UPDATE inventory SET reserved = reserved + 1 WHERE lot=$1 AND type=$2 AND slot=$3 AND reserved < capacity - walkin_buffer` (atomic conditional update) or a Postgres exclusion constraint on time ranges if assigning specific spots. Hold with expiry while paying (pending → confirmed, released by a reaper).
- **Real-time availability**: lot controllers emit events; availability service keeps counters; it's **eventually consistent** and that's fine (the display says "~12 free"); the authoritative check happens at the gate/reservation.
- **Payments**: via a PSP (Stripe/Adyen), idempotency keys on every charge, webhook to confirm, pre-authorisation at reservation and capture at exit. Never store card data (PCI scope).
**Failure modes**: lot offline (gates keep working with the local DB, sync later; conflicts resolved by "physical reality wins"), double reservation (atomic update), payment webhook lost (reconciliation job with the PSP), sensor drift (periodic recount from cameras).
**Trade-offs/v1**: v1 count-based availability and reservations by spot type (not specific spots); later: specific spot assignment, dynamic pricing, EV charging integration.

### 3. Design a rate limiter as a shared service used by 200 microservices.
**Clarify**: what are the limit keys (per user, API key, tenant, IP, endpoint)? Limits configured centrally? How strict (is going 1% over OK)? Latency budget added per request (must be ~1ms)? Fail open or closed if the limiter is down? Global (multi-region) or per region?
**Numbers**: 200 services, say 500k total requests/s checking the limiter. A network call per request at that rate is expensive, so this decides the architecture.
**API**: `check(key, rule, cost=1) → {allowed, remaining, reset_at, retry_after}`. Config: `rules(rule_id, key_pattern, algorithm, limit, window, burst)`.
**Architecture options**:
- **Centralised service** (gRPC) backed by Redis: simple, exact, but adds a network hop and is a shared point of failure.
- **Library/sidecar in each service** that talks to a **shared Redis cluster** directly with atomic Lua scripts: removes one hop. The library is a dependency 200 services must upgrade (versioning pain), unless shipped as a sidecar/Envoy filter.
- **Envoy/service-mesh global rate limit service** (Envoy's `ratelimit` service): standard, language-agnostic, configured centrally. Good answer for 200 services.
- **Hybrid for scale**: **local token buckets** in each instance that take a **share** of the global limit and periodically sync with Redis (e.g. every 100ms or per batch of N requests). Almost no latency and survives Redis blips, at the cost of slight inaccuracy (bounded overshoot). That's what big systems do.
**Algorithm**: token bucket (bursts + average rate, O(1) state) in Redis via Lua for atomicity; sliding window counter as an alternative (Round 3 Q26). Keys sharded across a Redis Cluster by limit key, so no single shard is hot except for huge single keys (split those: `key:{0..N}` and divide the limit).
**Deep dives**: **failure policy**: fail **open** for most limits (better to let traffic through than take down 200 services when Redis dies), fail **closed** for limits that protect money or abuse-sensitive paths; timeouts of a few ms on the limiter call. **Config management**: rules in a central store, pushed to sidecars/clients (no restart). **Multi-region**: per-region limits (limit/N per region) instead of a global synchronous counter. **Observability**: allowed/denied per rule/key, top limited keys, limiter latency.
**Trade-offs**: accuracy vs latency vs availability. You can't have exact global limits with zero latency; pick "approximately correct, very fast, fails open".

### 4. Design a distributed job scheduler (cron-as-a-service) with at-least-once execution, 1M jobs, and per-second granularity.
**Clarify**: what is a "job": an HTTP callback, a message published to a queue, or code we run? (Callback/message is much simpler; we just trigger.) Max execution time? Can jobs overlap with their own previous run? Timezones and DST? Required precision (within 1s of schedule?)? Retries and missed-run policy (catch up or skip)?
**Numbers**: 1M jobs. If the average is once per minute, ~17k triggers/s on average; per-second jobs on a fraction add more; peaks at round times (`0 * * * *`: a big fraction fire at the top of each hour/minute: thundering herd). Design for ~50–100k triggers/s peak.
**API**: `POST /jobs {schedule (cron + tz) | run_at, target (url/topic), payload, retry_policy, concurrency_policy}`; `GET /jobs/{id}/runs`.
**Data**: `jobs(id, schedule, tz, target, next_run_at, status, version)`, `runs(job_id, scheduled_for, status, attempts, started_at, finished_at)` with **`UNIQUE(job_id, scheduled_for)`** (the idempotency key of a run).
**Architecture**: API → Postgres (jobs) → **scheduler nodes** that find due jobs → push "run" messages to a queue (Kafka/SQS) → **executor workers** that call the target and record results.
**Deep dives**:
- **Finding due jobs efficiently**: index on `next_run_at`; partition jobs into N **shards** (by `hash(job_id) % N`); each scheduler node owns a set of shards via leases (DB row leases or a coordinator like etcd/ZooKeeper; rebalance on node failure). Each node loops every ~100–500ms: `SELECT ... WHERE shard IN (mine) AND next_run_at <= now() + 1s FOR UPDATE SKIP LOCKED LIMIT 1000`, enqueues runs, and advances `next_run_at` to the next occurrence **in the same transaction**. Alternative for second-level precision: a **timing wheel** in memory per node loaded with the next minute's jobs.
- **At-least-once**: the run record (`UNIQUE(job_id, scheduled_for)`) is inserted and the message published via an outbox; executors ack only after completion; a run without a completion before its timeout is retried. Consumers/targets must be idempotent and receive `scheduled_for` + run ID to dedupe. Exactly-once is impossible end to end.
- **Thundering herd at :00**: spread enqueuing slightly (jitter allowed per job), executor autoscaling ahead of known peaks (schedules are known in advance, so you can precompute the load curve!), and rate limits per target.
- **Time handling**: store schedules with timezone; compute next run in that tz (DST gaps/overlaps: decide whether a 2:30am job runs on DST day); use UTC internally.
**Failure modes**: scheduler node dies (its shard leases expire, another node takes over; runs not yet enqueued get enqueued late, so missed-run policy matters), queue backlog (alert on lag between `scheduled_for` and actual start), target down (retries with backoff, DLQ), clock skew between nodes (use DB time `now()` as the authority).
**Trade-offs/v1**: v1 Postgres + `SKIP LOCKED` polling handles far more than people expect; move to sharded timing wheels only if polling can't keep the precision.

### 5. Design a notification service: email, SMS, push, in-app. Templating, preferences, quiet hours, dedupe, and delivery guarantees.
**Clarify**: who sends (internal services via API/events)? Volumes per channel? Transactional (OTP, policy issued) vs marketing (different rules, opt-in, unsubscribe)? Latency needs (OTP within seconds)? Multi-language? Delivery tracking needed?
**Numbers**: say 10M notifications/day ≈ 115/s average, peaks 10× (campaigns). Provider limits matter more than our throughput (SES/SendGrid rate, SMS throughput per number, APNs/FCM).
**API**: `POST /notifications {idempotency_key, user_id, type, data, channels?, priority}`. Services send an **intent** ("policy_issued for user X with data Y"), not a rendered email; the notification service decides channels and content.
**Data**: `templates(type, channel, locale, version, body)`, `preferences(user_id, type/category, channel, enabled, quiet_hours, tz)`, `notifications(id, idempotency_key UNIQUE, user_id, type, status)`, `deliveries(notification_id, channel, provider, provider_msg_id, status, attempts)`.
**Architecture**: API/event consumer → **dedupe** (idempotency key) → persist → **router** (preferences, quiet hours, channel selection, rate limits/frequency caps) → **per-channel queues** (email, SMS, push, in-app) → **channel workers** (render template, call provider) → provider webhooks (delivered/bounced/opened) → status updates. In-app: written to a per-user inbox table + pushed over websocket/SSE.
**Deep dives**:
- **Preferences & quiet hours**: evaluated at send time; quiet hours → **schedule** for the end of the quiet window (delayed queue / scheduler), except critical transactional types (security alerts, OTPs) which bypass. Mandatory messages (legal notices) can't be disabled.
- **Dedupe**: (1) idempotency key from the caller (`UNIQUE` constraint) prevents duplicate sends from retries; (2) content-level dedupe/collapse (same type + entity within N minutes → one notification, or a digest).
- **Delivery guarantees**: at-least-once internally (queues with acks, retries with backoff, DLQ), provider message ID stored to avoid resending after a crash between "provider accepted" and "we recorded it" (check status before retry where the provider supports it). **Fallback**: push fails/not delivered → SMS for critical messages. Note: "delivered" for email is never certain (spam folders); track bounces and complaints and suppress bad addresses (a suppression list protects sender reputation).
- **Templating**: versioned templates per locale and channel, rendered with a sandboxed engine (Jinja sandbox), previewable, with a test-send function.
**Failure modes**: provider outage (multiple providers with failover per channel), provider throttling (per-channel rate limiter), template render errors (validate at publish time), runaway sender spamming users (per-user frequency caps, per-service quotas).
**v1/later**: v1 email + in-app with one provider each; later SMS/push, digests, A/B testing of templates, analytics.

### 6. Design a file upload + processing service (S3/Blob, 5GB files, resumable, virus scan, transcode, webhook on complete).
**Clarify**: file types (video → transcode)? Upload from browsers or servers? Expected volume and sizes? Processing latency requirements? Retention? Multi-tenant?
**Numbers**: say 100k uploads/day, avg 200MB, max 5GB → 20TB/day ingest. Bandwidth ≈ 2Gbps average, which **must not go through our API servers**.
**API**:
- `POST /uploads {filename, size, content_type, checksum}` → `{upload_id, part_size, presigned part URLs}` (S3 multipart upload) or an Azure Blob SAS URL with block uploads.
- Client uploads parts **directly to storage**, retrying failed parts (resumable); `GET /uploads/{id}` lists parts already uploaded (for resume after a crash).
- `POST /uploads/{id}/complete {parts: [etag...]}` → storage assembles the object.
- `GET /files/{id}` status; webhook registration per tenant.
**Data**: `uploads(id, tenant, key, size, checksum, status: initiated|uploaded|scanning|processing|ready|failed|quarantined)`, `processing_jobs(file_id, step, status, attempts)`.
**Architecture**: API issues presigned URLs → storage (S3/Blob) **quarantine bucket** → "object created" event (S3 events/Event Grid) → queue → **pipeline**: verify checksum → **virus scan** (ClamAV workers or a managed scanner like Defender for Storage) → if clean move to the clean bucket, else quarantine + notify → **transcode** (FFmpeg workers on spot instances / managed MediaConvert) producing renditions → update status → **webhook** to the tenant.
**Deep dives**:
- **Resumable 5GB**: multipart: parts of 8–100MB uploaded in parallel, each retried independently; the upload ID persists for days; abort incomplete multipart uploads with a lifecycle rule (otherwise you pay for orphan parts).
- **Processing pipeline**: an orchestrated workflow (Step Functions/Durable Functions/Temporal or a state machine in DB) since steps are long and must retry independently; workers autoscale on queue depth; transcode is CPU/GPU heavy → spot instances with checkpointing per rendition; large files are streamed, not loaded into memory.
- **Webhooks**: signed (HMAC), at-least-once with retries and backoff, idempotent event IDs, a delivery log + manual re-send, DLQ.
- **Security**: presigned URLs short-lived and scoped to one key; max size enforced in the presigned policy; files are untrusted until scanned (never served before); content-type sniffing, not trusting the extension.
**Failure modes**: client abandons (lifecycle cleanup), scanner backlog (files stay unavailable; alert on age), transcode failure on corrupt input (mark failed with a reason, notify), duplicate events from storage (idempotent steps keyed on file ID + step).
**v1/later**: v1 single-part for small files + multipart for large, scan, one rendition; later adaptive bitrate renditions, thumbnails, CDN delivery with signed URLs.

### 7. Design an idempotent payment/transaction ledger. Double-entry, no lost money, reconciliations.
**Clarify**: internal wallet/ledger or real money movement through banks/PSPs? Currencies? Volume? Who reads balances and how fresh must they be? Regulatory requirements (audit, retention)?
**Numbers**: say 1k transactions/s peak, each 2+ entries. Ledgers are about **correctness**, not throughput; a well-designed Postgres handles this.
**Principles**: (1) **double-entry**: every transaction is a set of entries that **sum to zero** (money moves between accounts, never appears/disappears); (2) **append-only and immutable**: never update or delete an entry, corrections are new reversing entries; (3) **idempotent**: every request carries an idempotency key; (4) amounts as **integers in minor units** (cents) or `NUMERIC`, never floats, and always with a currency.
**Data**:
```
accounts(id, type: asset|liability|revenue|expense, currency, owner, ...)
transactions(id, idempotency_key UNIQUE, type, status, created_at, metadata)
entries(id, transaction_id, account_id, amount_minor BIGINT, currency, created_at)   -- debits positive, credits negative
balances(account_id PK, balance_minor, version)   -- derived, maintained in the same transaction
```
**Write path**: in **one DB transaction** (serializable or with row locks on the balance rows, locked in a consistent order by account ID to avoid deadlocks): insert the transaction (unique idempotency key → a retry finds the existing one and returns its result), insert entries, check they sum to zero (constraint/trigger or app check), update balances with constraints (e.g. `CHECK (balance >= 0)` for accounts that can't go negative), commit.
**Deep dives**:
- **External money movement** (PSP/bank): model it as a state machine (`pending → settled/failed`) with **holds**: debit the user into a "pending outgoing" account first, call the PSP with an idempotency key, on confirmation (webhook or polling) move from pending to the settlement account; on failure reverse. Never lose track of in-flight money: a pending state is always visible.
- **Reconciliation**: daily (or continuous) job comparing the ledger to external statements (PSP settlement reports, bank statements): match by reference ID, amount, date; unmatched items go to an exceptions queue for humans. Also internal invariant checks: sum of all entries = 0; balance table = sum of entries per account (recompute and compare).
- **Hot accounts** (one company account receiving thousands of entries/s): row lock contention on its balance → shard the account into sub-accounts, or compute its balance asynchronously from entries.
**Failure modes**: crash mid-transaction (DB atomicity), retries (idempotency), PSP timeout with unknown outcome (query the PSP by idempotency key before retrying), duplicate webhooks (dedupe on event ID), clock/order issues (use transaction IDs/sequence for order).
**Trade-offs**: strong consistency over availability (a ledger must reject rather than guess); event-sourced by nature (entries are the events, balances are projections).

### 8. Design a feature flag service - low latency reads, global, with instant kill switch.
**Clarify**: server-side evaluation only or also clients (mobile/web)? Targeting rules (percentage, user attributes, tenants)? Number of flags and evaluation rate? How "instant" is the kill switch (seconds)? Audit requirements?
**Numbers**: thousands of flags, but **millions of evaluations/s** across all services. So evaluations **must be local (in-process)**, never a network call per check.
**Data**: `flags(key, type: bool|variant, default, enabled, rules (JSON: targeting conditions + percentage rollouts), version, updated_by, updated_at)`, plus an audit log of every change.
**Architecture**:
- **Control plane**: admin UI + API → flag store (Postgres) → on change, publish the new **ruleset snapshot** (versioned) to a distribution layer.
- **Distribution**: SDKs in each service hold the full ruleset **in memory** and receive updates by **streaming** (SSE/websocket/gRPC stream from a regional relay) with **polling as a fallback** (every 30s, using ETags). Snapshots also cached in a CDN/object storage per region for bootstrap.
- **Evaluation in the SDK**: rules evaluated locally in microseconds; percentage rollout by `hash(flag_key + unit_id) % 100` (deterministic, sticky).
- **Client-side (browser/mobile)**: evaluate on the server or edge for that user and send only the user's flag values (don't ship all rules and targeting data to clients).
**Deep dives**:
- **Instant kill switch**: a change pushes via streaming to all SDKs within ~1–2 seconds globally; SDKs that are disconnected pick it up on the next poll. Kill switches should be simple boolean flags evaluated first, with no complex rules.
- **Availability**: the flag service going down must **never** break the apps. SDKs keep the last known ruleset (and can persist it to local disk) and fall back to **code defaults**; startup with no connection uses defaults or a bundled snapshot. The safe default for each flag is chosen deliberately (usually "off" for new features).
- **Consistency**: eventual (seconds) is fine; include the ruleset version in logs/metrics to debug which version a request saw.
- **Governance**: audit log, approvals for production changes on sensitive flags, flag ownership and expiry dates, stale-flag reports.
**Trade-offs/v1**: v1 polling every 10–30s is often enough; add streaming when kill-switch speed matters. Buy (LaunchDarkly/Unleash/Flagsmith) vs build: usually buy or self-host Unleash; building is justified only with special constraints.

### 9. Design a real-time collaborative dashboard (many readers, live updates, 50k concurrent connections).
**Clarify**: "collaborative" = many viewers of the same live data, or many editors of the dashboard itself (that's a different, harder problem: CRDT/OT)? Update frequency of the data? Latency target (sub-second)? Per-user permissions on data? Number of distinct dashboards?
**Numbers**: 50k concurrent connections. A modern async server handles ~10–50k websocket connections per node depending on message rate, so plan ~5–10 nodes with headroom. If each dashboard updates once per second with ~2KB messages and every connection receives every update, 50k × 2KB/s = 100MB/s egress: fan-out is the real cost.
**Transport**: **SSE** if updates are one-way server → client (simpler, works over HTTP/2, automatic reconnect with `Last-Event-ID`); **WebSockets** if clients also send frequently (edits, cursors). Fall back to long polling for restrictive networks.
**Architecture**: data sources → ingestion → **aggregation** (stream processor or periodic queries) → **pub/sub backbone** (Redis Pub/Sub / Redis Streams / NATS / Kafka) with **one topic per dashboard/widget** → **connection gateway nodes** (stateless apart from connections) subscribe to the topics their connected clients need and fan out to sockets. Load balancer with websocket support; no sticky sessions needed if any gateway can subscribe to any topic.
**Deep dives**:
- **Compute once, fan out many**: never let 50k clients each query the DB. Each widget's data is computed **once** per update interval and published; gateways just forward.
- **Initial state + deltas**: on connect, client gets a snapshot (from a cache) then deltas with sequence numbers; on reconnect, resume from the last sequence (or resync from snapshot if too old).
- **Backpressure / slow clients**: bounded per-connection buffers; if a client can't keep up, **drop intermediate updates and send only the latest state** (dashboards care about the latest value, not every value), or disconnect.
- **Reconnect storms**: after a deploy or gateway crash, thousands reconnect at once → jittered client backoff, graceful draining (Part A Q30), autoscaling on connection count.
- **Auth**: authenticate at connect (token), authorise each subscription (can this user see this dashboard?), re-validate periodically for long connections.
- **Collaborative editing of the dashboard layout** (if needed): last-write-wins per widget with versioning is enough for layout; true co-editing of text needs CRDTs (Yjs/Automerge).
**Failure modes**: pub/sub down (gateways serve last snapshot, show "stale" indicator), gateway node lost (clients reconnect elsewhere), hot dashboard (one topic with 40k subscribers is fine for pub/sub; it's the gateways' fan-out that scales horizontally).

### 10. Design an audit log service that is append-only, tamper-evident, queryable, and retains 7 years of data cheaply.
**Clarify**: what events (data access, changes, admin actions, logins)? Volume? Query patterns (by user, by resource, time range; for investigations and auditors, not high QPS)? Who may read it? Legal hold requirements? Does "tamper-evident" need external proof (regulator)?
**Numbers**: say 50M events/day, ~1KB each → 50GB/day raw, ~18TB/year, ~130TB for 7 years before compression (Parquet/columnar compression ~5–10× → ~15–25TB). Writes ~600/s average, low query QPS.
**Event schema**: `event_id, timestamp, actor (user/service, IP, user agent), action, resource (type, id, tenant), outcome, request_id, before/after or diff (or a reference), source service, schema_version`.
**Architecture**:
- **Ingestion**: services emit events through an SDK → durable queue (Kafka/Event Hubs) → ingestion workers. Producers must not lose events: write locally with an outbox when the queue is unreachable. Audit for critical actions may need to be **synchronous** (no action without its audit record).
- **Hot store** (recent ~90 days): searchable store for investigations: OpenSearch/Elastic, ClickHouse, or Azure Data Explorer, indexed by actor, resource, time.
- **Cold store** (7 years): immutable object storage (S3 Object Lock / Azure Blob immutable storage in **WORM compliance mode**), events batched into **compressed Parquet files** partitioned by date/tenant, lifecycle to cool/archive tiers. Queryable on demand with Athena/Synapse/Trino/DuckDB.
**Tamper-evidence**:
- **Hash chaining**: each batch (e.g. per minute per partition) gets `hash = H(batch_content + previous_batch_hash)`; altering or deleting any old record breaks the chain from that point.
- **Periodic anchoring**: publish the latest chain hash (or a **Merkle root** of the day's batches) to a separate, independently controlled place (a different account, a signed timestamping service, or a ledger DB like Azure Confidential Ledger / AWS QLDB-style). An attacker would need to compromise both.
- **Signatures** on batches with a KMS key; verification job re-computes chains regularly and alerts on mismatch.
- **Access control**: writers can only append (no update/delete permissions), WORM storage prevents deletion even by admins until retention expires; reads are themselves audited.
**Deep dives**: schema evolution (versioned schemas), PII in audit logs (minimise, encrypt sensitive fields, but GDPR erasure conflicts with immutability: store PII separately and keep pseudonymous IDs in the log, so erasing the mapping "forgets" the person), retention enforcement (lifecycle policies delete after 7 years; legal holds override).
**Trade-offs**: hot searchability is expensive, so keep it short; cold queries are slow (minutes) but cheap, which is fine for auditors.

### 11. Design a news recommendation serving system for 100M requests/day. Push on: peak RPS, candidate generation vs ranking, precomputed vs online, cold start for new users AND new articles, feature store, cache hit ratio, freshness vs cost, and how you A/B test ranking changes.
**Clarify**: what's a "request" (a feed load returning 20–50 articles)? Number of users (DAU)? Article inventory and churn (news is very short-lived: hours)? Latency budget (p99 < 100–150ms for the feed)? Languages/regions? What signals exist (clicks, dwell time, shares)?
**Numbers**: 100M/day ÷ 86,400 ≈ **1,160 RPS average**. News traffic is peaky (morning, evening, breaking news): **peak 3–5× → ~4–6k RPS**, design for ~10k. Say 30M DAU, 50k new articles/day, ~500k active articles. Each request scores maybe ~500 candidates → 5M scorings/s at peak if done online, which is why you need staged retrieval and caching.
**API**: `GET /feed?user_id&page_token&section` → list of article IDs + metadata + a `rec_request_id` for attribution. Events: `POST /events {user_id, article_id, type: impression|click|dwell, rec_request_id}`.
**Architecture (the standard two-stage funnel)**:
1. **Candidate generation** (thousands → ~500): several cheap retrievers merged: trending/popular per region and section (precomputed every minute), recent articles in the user's preferred categories/topics, collaborative filtering / embedding nearest neighbours (user embedding vs article embeddings in an ANN index like FAISS/ScaNN/Vertex Matching Engine), follow-ups on stories the user read.
2. **Ranking** (~500 → 50): a model (GBDT like LightGBM, or a small neural net) scoring each candidate with user features + article features + context (time, device); served by a model server.
3. **Re-ranking / business rules**: diversity (not 10 articles on the same story), freshness boost, dedupe already-seen articles, editorial pins, safety filters.
**Precomputed vs online**:
- **Precomputed (batch)**: user embeddings/profiles updated hourly/daily; per-user candidate lists for heavy users; popular/trending lists every minute. Cheap per request, but staler.
- **Online**: ranking at request time with fresh context and **real-time features** (articles clicked in this session, last 30 minutes), because news freshness matters: an article from 2 hours ago may already be irrelevant.
- Hybrid is the answer: precompute **candidates and slow features**, rank **online**.
**Feature store**: offline store (BigQuery) for training + **online store** (Redis/Bigtable) for serving with the **same feature definitions** (avoids training/serving skew). Real-time features (recent clicks, article CTR in the last 10 min) computed by a streaming job (Pub/Sub → Dataflow) and written to the online store.
**Cold start**:
- **New user**: popular/trending by region, language and time; device/location context; onboarding topic picks; a fast **session-based** model that adapts after the first 2–3 clicks (bandit-style exploration).
- **New article**: no click history → content-based features (category, entities, embedding of title/body, publisher quality), an **exploration slot** (a small % of impressions given to fresh articles, e.g. epsilon-greedy / Thompson sampling) to quickly learn CTR, and a freshness prior.
**Caching & cache hit ratio**: personalised feeds have low cache reuse across users, so cache **components**, not whole responses: trending lists (≈100% hit), article metadata (very high hit, small set of hot articles), user profile/features (per user, short TTL), and a user's **ranked feed for a few minutes** (pagination and refreshes reuse it). A realistic hit ratio on per-user feed cache might be 30–60% (refreshes, back navigation); on article metadata 95%+. Fallback when the ranker is slow/down: serve the cached feed or trending (graceful degradation; this is an **AP** system, Round 3 Q43).
**Freshness vs cost**: more frequent recomputation (embeddings every hour vs every day; real-time features) costs compute; quantify with A/B tests: does hourly refresh improve CTR enough to pay for it? Typically real-time is worth it for article-side signals (trending) more than for user embeddings.
**A/B testing ranking changes**: deterministic assignment by user hash into experiment buckets; log `rec_request_id`, model version and experiment arm with every impression; metrics: CTR, dwell time, return rate (D1/D7 retention), diversity, and guardrails (latency, errors); run long enough for novelty effects to wear off; **interleaving** (mixing results from two rankers in one list) for faster, more sensitive offline-to-online comparison. Offline evaluation (NDCG/AUC on logged data) before any online test.
**Your story:** this is the resume claim the interviewer will attack. Know: real peak RPS, how many pods on GKE, what was precomputed vs online in your system, what Redis held, how Postgres/Mongo/Pub/Sub were used, cache hit ratio, latency p99, and what "single-handedly" covered. If the actual system was simpler (e.g. precomputed lists served from Redis), say so confidently and explain why it was the right call.

### 12. Same system, now: the ML team wants to ship a new model twice a day, and you must support shadow traffic and instant rollback. Design the model serving layer.
**Requirements**: frequent deploys without engineer involvement, safe validation on real traffic before exposure, rollback in seconds, reproducibility (which model served which request).
**Components**:
- **Model registry** (MLflow / Vertex AI Model Registry): every model is an immutable versioned artifact with metadata (training data window, feature list and versions, offline metrics, owner), and stages (staging/production).
- **Automated validation pipeline** on registration: offline metrics vs current production model (must not regress beyond a threshold), schema check of input features (feature names/types match the feature store), latency/size benchmarks, smoke predictions.
- **Model server**: a serving framework (Triton, TF Serving, KServe, BentoML, or a FastAPI service that loads models) that can host **multiple model versions at once**, each addressable by version.
- **Routing layer** (in the ranking service or the serving gateway): traffic split config: `{production: v41: 95%, canary: v42: 5%, shadow: v43}`. Config in a flag/config service, so changing it is instant.
**Shadow traffic**: for each request, the router **also** sends the same features to the shadow model **asynchronously** (fire-and-forget, never on the critical path, with its own timeout); the shadow's results are **logged, not served**. Compare: score distributions, ranking overlap with production (e.g. Jaccard/rank correlation of top-20), latency, errors. This catches broken models (e.g. a feature pipeline bug causing all-zero scores) before any user sees them. Cost: up to 2× inference; sample shadow traffic (10–20%) if expensive.
**Rollout**: shadow (hours) → **canary 1–5%** with automated comparison of online metrics (CTR, latency, errors) against control → ramp up → 100%. Automatic rollback if guardrail metrics breach.
**Instant rollback**: the previous version stays **loaded and warm** in the server; rollback = flip the routing config back (seconds, no deploy). Keep the last N versions loaded/available.
**Consistency details**: models must be compatible with the **feature versions** they were trained with (pin feature definitions per model; a feature pipeline change is itself a versioned rollout); log `model_version` with every impression for attribution and debugging; warm up a newly loaded model (load + a few predictions) before routing traffic to it; pods load models from the registry at startup and on config change (hot reload), so twice-a-day model updates don't need container redeploys.
**Ownership**: the ML team owns models and promotion decisions through the pipeline (self-service); platform owns the serving infra, routing and guardrails (see Q20).

**Pipeline** (each stage a queue + autoscaled workers; raw files kept for replay):
1. **Ingestion adapters** per source → normalise into a common envelope (`source, source_candidate_id, file, metadata`) → raw blob storage + ingestion record. Uploads go directly to blob via SAS URLs.
2. **File processing**: type detection, virus scan, conversion (DOC/DOCX → text via LibreOffice/python-docx; PDF text layer via pdfplumber/PyMuPDF; scanned/no text layer → OCR with Azure Document Intelligence/Tesseract). Language detection.
3. **Structured extraction**: name, contacts, experience (companies, titles, dates), education, skills → JSON with confidence scores. 4. **Candidate dedupe / entity resolution**: same person from 3 job boards. **Blocking** first (candidates sharing normalised email or phone → near-certain match; otherwise same name + overlapping employer/education), then a scoring model over field similarities (name fuzzy match, email, phone, employment history overlap, embedding similarity of the resume). High-confidence → merge automatically into one **candidate profile** with multiple source documents; medium → a review queue. Keep merges reversible (link table, not destructive overwrite).
5. **Embedding**: embed the profile (and sections: skills, experience summary) with a text embedding model; store in a vector index (pgvector / OpenSearch k-NN / Azure AI Search).
6. **Matching against JDs**: JDs are also parsed (required skills, years, location, seniority) and embedded. **Retrieval**: for each new candidate, ANN search for the top-k JDs (and for each JD, top-k candidates when a recruiter opens it) + **hard filters** (location, work authorisation, required certifications). **Ranking**: a scoring model combining semantic similarity, skill overlap (required vs nice-to-have), experience years, title/seniority match, recency.
7. **Results**: match scores stored; recruiters see ranked lists; notifications for strong matches.

- With a GBDT ranker, per-feature contributions (SHAP values) map to human-readable reasons.
- Highlight evidence: the resume snippets where skills were found.
- Log model version and inputs for every score, to reproduce it later; keep humans as decision makers (the system ranks/suggests, it doesn't auto-reject), and run **bias audits** (selection rates across groups; don't use protected attributes or proxies like names/photos/age signals in features).
**Failure modes**: parse failures (DLQ + fallback to raw text + a manual queue), wrong merges in dedupe (reversible, audit), embedding model change (re-embed everything in background with a versioned index, then switch: blue/green index), duplicate events (idempotent stages keyed on file hash).

- **Write conflicts**: true multi-primary Postgres (BDR/pgEdge/EDB, or logical replication both ways) means two regions can update the same row concurrently → conflict resolution (last-write-wins loses data; custom merges are complex). Unique constraints and sequences across regions break (use UUIDs). Options:
  1. **Single write region, read replicas everywhere**: writes go to (or are proxied to) the primary region; reads served locally. Simple, but writes from far regions have cross-region latency (~70–150ms), and the primary region is a SPOF for writes (promote a replica on failure).
  2. **Partition data by home region** ("geo-partitioning"): each tenant/user has a home region, which owns its writes; requests are routed to the home region for writes. No conflicts because each row has one writer. Works well for multi-tenant SaaS, and naturally supports data residency.
  3. A **distributed SQL** DB designed for this (CockroachDB, YugabyteDB, Spanner, Aurora DSQL), with Postgres compatibility: consensus-based, strongly consistent, but cross-region write latency and cost, and compatibility gaps.
- **Data residency**: EU data must stay in the EU, so global replication of everything is forbidden; geo-partitioning by tenant region is required, and only non-personal/global data is replicated everywhere.
- **Session affinity / read-your-writes**: a user writes in region A, the next request lands in region B reading a lagging replica → stale data. Fix: stateless JWT sessions, routing users consistently to their home region, read-your-writes routing (Round 3 Q47).
- **Caches, queues, background jobs**: per-region; avoid jobs running twice (one region owns scheduled jobs, or regional leader election); cache invalidation across regions.
- **Failover testing**: failover must be practiced (Part A Q34): promote the replica, re-route, deal with the replication lag lost (RPO), then **fail back**, which is often harder. Split-brain prevention (fencing the old primary so it can't accept writes).
**When active-passive is the correct, boring answer**: most of the time. If the goal is **availability/DR** rather than global latency, and the business can accept an RTO of minutes to an hour and an RPO of seconds to minutes, then: one active region serving all traffic, a warm standby region with an async Postgres replica and pre-provisioned (scaled-down) infra, DNS/Front Door failover. Far simpler, cheaper, no write conflicts, and easy to reason about. Go active-active only with a concrete need (latency for globally distributed users on write-heavy paths, regulatory residency with local processing, or an RTO near zero) that justifies the cost and complexity.

**Architecture**:
- **Authoring & build pipeline** (offline): business users upload workbooks → **transpiler** (Round 3 Q54) generates a Python module + input/output schema → differential tests against Excel (Round 3 Q62) → semantic + behavioural diff vs the previous version (Round 3 Q64) → approval (maker-checker) → **publish an immutable rater artifact** (module + metadata + workbook hash) to an artifact store (blob storage, versioned, WORM) and register it in the **rater registry** (Postgres: product, jurisdiction, version, effective_from/to, status, artifact hash).
- **Quote service** (online, stateless, horizontally scaled): validates inputs against the rater version's schema → **resolves the rater version** → loads the module (cached in-process) → `rate(inputs)` → persists the quote → returns.
- **Postgres** for quotes and the registry; **blob storage** for artifacts; **cache** in-process (+ Redis optional).
**Versioning of rules**: each (product, jurisdiction) has a sequence of immutable versions with **effective dating**: version resolution uses the **policy effective date** (not today's date), so a rate change "effective 1 April" applies to policies incepting on/after 1 April even if quoted in March. Versions are never edited; corrections are new versions. (Bitemporal model: Round 3 Q48.)
**Deterministic replay**: the quote row stores `inputs` (as validated), `outputs`, `rater_version_id`, artifact hash, **engine/runtime version** (container image digest), and the effective date used. Replay = load that exact artifact (hash-verified) in that runtime version and run `rate(inputs)`; result must equal stored `outputs`. Keep old runtime images and artifacts forever (or for the retention period: often 7–10+ years). Pure-function raters: no clocks, no randomness, no external calls inside `rate()`; external data (e.g. a postcode risk score from a third party) is fetched **before** rating and stored as part of the inputs.
**Caching**: (1) loaded rater modules per process, keyed by version (load once, LRU by version, preloaded for active versions at startup); (2) optional result cache keyed on `(rater_version, hash(canonical inputs))` since `rate` is pure, useful for brokers re-quoting identical risks; (3) registry lookups cached with short TTL. Never cache across versions.
**Rolling out a rule change without breaking in-flight quotes**:
- New version published with an effective date; **existing quotes stay pinned** to the version they were rated with. Binding a quote uses its stored premium (within its validity period), **not** a re-rate with the new rules. If the business requires re-rating at bind after a change, that's an explicit, visible "requote" step.
- Activation is a registry change (no code deploy); pods pick up new versions within seconds (cache refresh / event).
- Safety: **shadow-rate** with the new version for a period (compute both, log differences, serve the old) before the effective date; compare distributions; then activate. Rollback = deactivate the version (quotes made with it remain valid and reproducible).
- Schema changes in inputs (new required field) are coordinated with the API consumers: versioned input schemas per rater version; the API validates per version.
**Failure modes**: a rater throws or returns an Excel error for some inputs (structured domain error + alert, never a 500 with a wrong premium), a bad version published (approval + shadow + instant deactivation), artifact store unavailable (pods keep loaded modules; preload active versions), DB down (quotes can't be persisted, so fail closed: never return an unpersisted quote, since it couldn't be reproduced).
**Trade-offs**: codegen vs interpreter (Round 3 Q61); strict immutability adds storage but is non-negotiable for regulated pricing.

### 25. Design the human-in-the-loop review layer for that extraction: how do you decide what needs review, how do you measure model quality over time, and how do you feed corrections back?
**Deciding what needs review**:
- **Field-level confidence thresholds**, calibrated per field (a model's raw confidence isn't a probability: calibrate using reviewed data so that "0.9" really means ~90% correct). Critical fields (sum insured, effective date, insured name) get stricter thresholds than minor ones.

- **Model disagreement**: if two extractors (e.g. a form model and an LLM) disagree on a field → review.
The decision unit is the **field**, not the whole document: reviewers see the document with only the uncertain fields highlighted, which makes review fast.
**Reviewer UX**: side-by-side document viewer with highlighted source regions, keyboard-first correction, "accept all high-confidence", reasons for corrections (wrong value, wrong field, not present in document), time tracking.
**Measuring model quality over time**:
- Ground truth = reviewed/corrected values (from both triggered reviews and random samples).
- Metrics per **field, document type, broker/source, and model version**: precision/accuracy, **straight-through processing rate** (fraction needing no human touch), correction rate, review time per document, SLA impact.
- **Drift detection**: monitor input distributions (new form layouts from a broker, language, scan quality) and confidence distributions; a sudden drop in confidence or rise in corrections for one broker = new template.
- A fixed **golden evaluation set** (labelled documents) to benchmark every new model/prompt version offline before rollout; online comparison via shadow mode.
- Dashboards with trends, and alerting on degradation.
**Feeding corrections back**:
- Store every correction as a **labelled example**: document, page/region, model output, corrected value, reviewer, timestamp, model version.
- **Short loop** (days): adjust prompts, few-shot examples, validation rules and **per-broker templates/mappings**; recalibrate thresholds with the new data.

- Close the loop visibly: show reviewers/teams that the STP rate is rising, which keeps them engaged.
**Thresholds as a business dial**: lower thresholds → more automation but more errors; the business chooses the operating point per field using the precision/recall curve from reviewed data.

**Logging & monitoring**: central Log Analytics workspace (AWS: central log archive account) receiving **activity logs, resource diagnostic logs, Entra sign-in/audit logs**, firewall logs; **Defender for Cloud** (AWS Security Hub/GuardDuty); immutable long-term archive of audit logs in a storage account in the management subscription; alerting on security events.
**Cost allocation**: mandatory **tags** (`product`, `env`, `owner`, `cost-center`) enforced by policy; budgets and anomaly alerts per subscription; cost dashboards per product/team; reserved capacity managed centrally.
**Guardrails (preventive + detective)**: **Azure Policy** (AWS SCPs + Config rules): allowed regions (data residency), allowed SKUs (no surprise expensive VMs), require tags, deny public IPs on VMs / public storage access, require encryption, require diagnostic settings, deny creation of resources outside approved patterns; Defender/Config compliance dashboards. Everything via IaC and PRs (policy-as-code).
**Day 1 vs day 100**:
- **Day 1 (minimal but correct foundations; hard to change later)**: management group/subscription structure, IP address plan, Entra SSO + MFA + PIM, hub with firewall/private DNS, prod and non-prod spokes, Key Vault, central logging, tag policy + region policy + basic deny policies, budgets, Terraform state and CI/CD with federated identity. Things that are **expensive to retrofit** go in on day 1: identity model, network address space, subscription boundaries, logging.
- **Day 100 (mature)**: full policy set with compliance reporting, Defender plans enabled with alert handling, a subscription vending machine (new product/team gets a compliant subscription via a PR), DR region and backup policies, cost optimisation (reservations, showback), SIEM integration (Sentinel), automated access reviews, landing-zone module versioning and upgrades, chaos/DR drills, documented golden paths for teams (Q35).

### 29. Design CI/CD for 30 microservices in a monorepo. Selective builds, shared libs, versioning, environment promotion, and how long a deploy takes.
**Repo layout**: `services/<name>/` (each with its Dockerfile, Helm chart/kustomize, tests), `libs/<name>/` (shared Python packages), `infra/`, `.ci/` (shared pipeline templates). Tooling: **uv workspaces** / Poetry / Pants / Bazel for dependency graphs in Python monorepos (Pants/Bazel give precise affected-target detection and remote caching; uv workspaces + a simple dependency map is enough at 30 services).
**Selective builds**: on each PR, compute the **affected set**: changed files → which services/libs they belong to → **plus all services that depend on a changed lib** (from the dependency graph). Only build/test/deploy the affected services. Path filters in GitHub Actions / ADO pipelines can work for simple cases; a dependency-graph tool is more reliable. Changes to shared CI templates or base images → rebuild all (or roll out in waves).
**Shared libs**: two models:
- **Source dependency (live at head)**: services import libs directly from the repo; a lib change triggers tests of every dependent service in the same PR. Atomic changes across lib + services, no version skew; the price is that a lib change must keep all 30 services green.
- **Versioned internal packages** published to a private registry; services pin versions and upgrade on their own schedule. Fewer surprises but version drift and the "diamond dependency" problem.
In a monorepo, **live at head** is usually the point of having one; use semver packages only for libs consumed outside the repo.
**Pipeline stages per affected service**: lint + type check (ruff, mypy) → unit tests → build container image (multi-stage, **BuildKit cache** / registry cache, base images prebuilt) → integration tests (testcontainers) → security scans (dependencies, image CVEs with Trivy, secrets scan, SAST) → push image tagged with **git SHA** (immutable) → deploy to **dev** automatically → contract tests / smoke.
**Versioning**: image tag = commit SHA (the artifact identity); human-readable release versions per service optional (semver tags or calendar versions), changelog generated from conventional commits. Deployed version per environment recorded in Git (GitOps repo/folder).
**Environment promotion**: **build once, promote the same image** through dev → staging → prod (never rebuild per environment). **GitOps** (Argo CD/Flux): promotion = a PR updating the image tag in the environment's config (automated for dev/staging, approval for prod); Argo syncs. Gates: automated tests in staging, required approvals for prod, change windows if needed, **canary** in prod with automatic analysis (Argo Rollouts) and auto-rollback.
**How long a deploy takes** (targets to state): PR CI for an affected service **< 10–15 minutes** (fast feedback matters most); merge to dev deployment ~15 minutes; prod rollout with canary analysis **~20–30 minutes**; total commit-to-prod well under an hour for routine changes; rollback in < 5 minutes (re-sync previous tag). Techniques: caching (dependency, Docker layers, test results via Pants/Bazel remote cache), parallel jobs per service, test sharding, slimmer images.
**Guard rails**: CODEOWNERS per service, required checks, merge queue (avoid "green PRs that break main together"), trunk-based development with feature flags, DORA metrics tracked (deployment frequency, lead time, change failure rate, MTTR).

### 33. Design the observability stack for a 40-service platform on a fixed budget. What do you sample, what do you keep, what do you drop, and what are the 6 alerts that page a human at 3am?
**Stack (budget-conscious)**: **OpenTelemetry** SDKs/auto-instrumentation in every service (vendor-neutral, so you can switch backends) → **OTel Collector** (agents per node + a gateway tier) where sampling/filtering/routing happens → backends. Cost-efficient self-hosted option: **Prometheus/Mimir** (metrics), **Loki** (logs), **Tempo** (traces), **Grafana** (dashboards/alerts), all using cheap object storage. Or a managed backend (Grafana Cloud, Datadog, Azure Monitor) with strict ingestion controls; the collector is your cost control point either way. Plus Sentry for errors (cheap, very high signal).
**What to sample**:
- **Traces**: **tail-based sampling** in the collector: keep **100% of traces with errors or high latency** (above p99 threshold), plus a small percentage (1–10%) of normal traces; always keep traces for low-volume critical endpoints. Head-based sampling at 100% of nothing is wasteful; tail sampling keeps the interesting ones.
- **Logs**: sample/rate-limit repetitive high-volume logs (e.g. keep 1 in 100 identical access logs for successful health-check-like requests, keep all errors).
**What to keep**:
- **Metrics**: RED metrics per service/endpoint, USE metrics for infra, business KPIs, SLO metrics: retained long (13 months, downsampled after 30 days). Metrics are the cheapest signal per insight: use them as the backbone.
- **Logs**: structured JSON with trace/request IDs; **errors and warnings fully**; info logs for key business events; retention tiered (7–14 days hot, 30–90 days cold, longer only for audit logs, which go to a separate cheap archive).
- **Traces**: 7–14 days.
**What to drop**:
- Debug logs in production (enable dynamically per service when investigating), health check and readiness probe logs/traces, noisy library logs, duplicate logs (both app and sidecar logging the same request), kube-system chatter.
- **High-cardinality metric labels** (user ID, request ID, full URL with IDs) → the #1 cause of metrics bills exploding; use route templates, and put per-user detail in traces/logs instead.
- Unused metrics (audit which series are never queried by dashboards/alerts and drop them at the collector).
**Budget control**: per-service ingestion quotas and dashboards showing each team's observability cost; alerts on ingestion spikes.
**The 6 alerts that page at 3am** (symptom-based, SLO-driven; everything else is a ticket or business-hours alert):
1. **Availability SLO burn rate** for user-facing APIs (fast burn: e.g. 2% of monthly error budget in 1 hour).
2. **Latency SLO burn rate** (p99 over target) for critical endpoints.
3. **Synthetic check failure** of the critical user journeys (login, quote, bind) from outside the platform: catches things internal metrics miss (DNS, certificates, CDN, auth).
4. **Async pipeline stalled**: age of oldest message / consumer lag over SLA on critical queues, or DLQ rapidly growing.
5. **Data-store danger**: primary DB unavailable/failover, replication lag beyond RPO, disk/storage > 90%, connection saturation.
6. **Security/certificate critical**: TLS certificate expiring within 72 hours without renewal (or a critical security alert from Defender/GuardDuty, depending on who's on call for security).
Each page has a runbook link, an owner, and is reviewed monthly: any alert that paged without action needed gets fixed or deleted.

### 35. Design a self-service internal developer platform: a new service goes from "git repo created" to "running in prod with monitoring" with no platform-team ticket. What are the golden paths?
**Principle**: the platform is a **product** for internal developers: opinionated golden paths make the right way the easy way; teams can deviate, but then they own the extra work.
**Components**:
- **Developer portal** (**Backstage** or Port): software catalog (every service with owner, docs, dependencies, on-call, dashboards), **scaffolder templates**, TechDocs.
- **Templates (golden paths)**: e.g. "Python FastAPI service", "Python worker (queue consumer)", "scheduled job", "frontend app". Each template creates in one click: a repo with standard structure, Dockerfile, tests, linting, **CI pipeline** (from shared templates), Helm chart/kustomize with sane defaults (resources, probes, PDB, HPA), OpenTelemetry instrumentation pre-wired, structured logging, default dashboards and SLO alerts, CODEOWNERS, catalog registration.
- **Infrastructure self-service**: developers request resources (Postgres DB, Redis, queue, storage bucket) **declaratively** in their repo (Crossplane claims, Terraform modules via a PR to an infra repo with automated approval for standard sizes, or Azure Service Operator) → provisioned with policies applied (encryption, private networking, backups, tags); credentials delivered via workload identity/Key Vault automatically.
- **Deployment**: GitOps (Argo CD) with environments created automatically (dev namespace on first push; prod via promotion PR); canary rollouts standard.
- **Guard rails, automatic**: policy-as-code (OPA Gatekeeper/Kyverno: no privileged containers, resource limits required, images only from the internal registry, required labels), image scanning, secrets scanning, cost tags, network policies by default.
- **Observability included**: dashboards (RED), log queries, traces, SLO definitions from the template; alert routing to the owning team's on-call.
**Flow ("repo created → prod with monitoring")**: developer picks a template in Backstage → repo + pipeline + catalog entry created → first commit deploys to dev automatically → declares needed DB in a manifest → provisioned in minutes → staging deployment on merge with automated tests → prod via promotion PR (approval by their own team, not the platform team) → dashboards and alerts already exist. **Target: under a day for a new service, with zero tickets.**
**Ownership**: platform team owns the templates, shared pipelines, clusters, policies, provisioning modules, portal, and the platform's reliability; product teams own their service code, configs, alerts tuning, and on-call. Templates are versioned; updates roll out to existing services via automated PRs (Renovate-style) so services don't drift.
**Measure the platform like a product**: time to first deploy for a new service, % of services on golden paths, deployment frequency, developer satisfaction surveys, number of platform tickets (should trend down).

### 37. Design multi-tenant infrastructure isolation for an insurance SaaS with clients who demand data residency in EU, UK and US, and one client who demands a dedicated stack.
**Clarify**: what must stay in-region (all customer data incl. backups and logs? just PII?)? Can support staff access data from other regions? Is the dedicated client also in one of the 3 regions? Shared global services (billing, identity)? Number of tenants per region?
**Architecture: "regional cells" (deployment stamps)**:
- One **stamp (cell)** per region: **EU (e.g. West Europe/Frankfurt), UK (UK South), US (East US)**. Each stamp is a complete, identical copy of the platform (app clusters, databases, storage, queues, search, logging) deployed from the **same IaC modules and the same container images**, with region-specific config. Data never leaves the stamp.
- **Within a stamp**: multi-tenant (pooled) model, typically row-level isolation with RLS or DB-per-tenant for larger clients (Round 3 Q32), per-tenant encryption keys optional (customer-managed keys in a regional Key Vault).
- **Dedicated client**: their own stamp (**"silo"**) from the same IaC (`stamp = dedicated-clientX`), in their required region, possibly in a separate subscription/account (and even their own tenant-managed keys). Same release pipeline deploys to it as just another stamp → no special snowflake code.
- **Global control plane** (minimal, holds **no customer data**): tenant directory/router (`tenant → stamp`), global DNS/front door that routes each request to the right stamp (by tenant subdomain like `clientx.app.com`, or by a tenant claim in the token), release orchestration, platform-level monitoring with aggregated, non-PII metrics.
- **Identity**: either per-stamp identity, or a global IdP if login data (email) is allowed to be global; many insurance clients bring their own IdP via SSO federation, which simplifies this.
**Data residency details** (where people slip up): **backups and DR replicas** must be in-region (e.g. EU backups to another EU region, UK paired with UK West, not to the US); **logs, traces and support tooling** contain PII and must stay in-region (regional observability backends; scrub PII before anything goes to the global plane); **third-party services** (LLM APIs, OCR, email) must be regional deployments (Azure OpenAI in EU/UK regions, EU data boundary); support access from other countries governed by contracts and access controls (JIT access, audited); Azure Policy "allowed locations" per stamp subscription.
**Operations**: deploy changes stamp by stamp (canary stamp first, ring-based rollout: internal → small region → others → dedicated client stamp per their change window); fleet-wide observability of health and versions; migrations run per stamp; cost tracked per stamp (the dedicated client's stamp cost is billed to them).
**Trade-offs**: more stamps = more operational overhead and higher fixed cost; mitigated by total automation (IaC + GitOps + identical stamps). Moving a tenant between stamps is a data migration project: design tenant export/import tooling early.

### 41. Design a compliance-ready (SOC2) logging & access-review system: who accessed what customer data, when, retained for how long, and how you produce an auditor report.
**What SOC2 auditors look for** (relevant Common Criteria: logical access CC6, monitoring CC7, change management CC8): evidence that access to customer data is **restricted, logged, reviewed, and that anomalies are acted on**, consistently over the audit period (Type II = over 6–12 months).
**What to log ("who accessed what, when")**:
- **Application data-access events**: user/service identity, tenant, action (view/export/modify/delete), resource type + ID, fields touched for sensitive data, timestamp, source IP, request ID, outcome. Emitted by a shared middleware/SDK on every data-access endpoint, including **admin/support tooling** (support staff viewing customer data is the key thing auditors probe) and bulk exports.
- **Infrastructure access**: cloud control-plane activity logs (who changed what), DB access logs (pgaudit for direct DB access by humans), Kubernetes audit logs, bastion/SSH/JIT elevation sessions, Key Vault access logs, Entra sign-in logs (MFA usage, failed logins).
- **Changes**: CI/CD deployment logs linked to approved PRs (change management evidence).
**Pipeline & storage**: events → durable queue → audit store: **immutable** (WORM blob / append-only, tamper-evident as in Q10), searchable hot tier (90 days–1 year), cheap cold tier for the rest. Clock-synchronised timestamps (UTC). Access to the audit logs themselves is restricted and logged.
**Retention**: SOC2 doesn't mandate a fixed period, but you need the full audit period available plus margin: commonly **1 year minimum for security/access logs** (often hot 90 days + archive 1–7 years based on contracts and other regulations; insurance and GDPR/financial regulations may require longer for some records, while PII minimisation argues for not keeping more than needed). Define it in a written retention policy and enforce with lifecycle rules.
**Access reviews**:
- **Periodic user access reviews** (quarterly): automated generation of review campaigns: each manager/system owner gets the list of who has access to which systems and roles (from Entra groups, cloud RBAC, DB roles, app admin roles) and must approve or revoke; revocations are executed automatically and logged. Tools: Entra ID Access Reviews, or a small internal tool pulling from the IdP + systems.
- **Joiner/mover/leaver automation**: access granted via groups tied to HR roles; leaver deprovisioning within 24h, evidenced by logs.
- **Privileged access**: JIT elevation (PIM) with justification and approval, time-bound, all sessions logged; break-glass usage alerts immediately.
- **Anomaly detection**: alerts on unusual data access (support user viewing many tenants, bulk exports, access outside working hours, access from new countries) → SIEM (Sentinel) → triage process with tickets as evidence.
**Producing the auditor report**:
- An **evidence pipeline**: scheduled queries generate reports per control and period: list of all privileged access sessions with approvals; access review campaigns with completion status and revocations; data-access logs filtered by support/admin roles; leaver deprovisioning timings vs HR dates; alert triage tickets; change approvals linked to deployments.
- Export as immutable, timestamped artifacts (CSV/PDF + hash) into an evidence repository; compliance automation tools (Vanta, Drata, Secureframe) can collect much of this continuously from cloud/IdP/GitHub APIs and map it to controls.
- For an ad-hoc auditor question ("show me everyone who accessed tenant X's data in March"): a query interface over the audit store, with results exported and the query itself logged.
